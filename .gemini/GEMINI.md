# Project GEMINI.md: oscss-elementor-bizjapan (AIDD 仕様)

本ファイルは、`oscss-elementor-bizjapan`（WordPress / Elementor 向けカスタムテーマ）プロジェクトにおける **AI駆動開発（AIDD: AI-Driven Development / Spec-Driven Development）運用憲法** および開発運用ルールを定義します。

---

## 📜 1. AIDD プロジェクト開発・ドキュメント運用憲章 (Project Charter)

本プロジェクトにおけるすべての開発行為は、以下の 4 大原則を不可侵の憲章として遵守します。

1. **第 1 条: 正本はコード (Code is Single Source of Truth)**
   ソースコード（PHPテンプレート、CSS、JS、およびテーマ構造）が常に一次情報（正本）である。コードとドキュメントに不整合が生じた場合は、実行コードを絶対正とする。
2. **第 2 条: ドキュメントは「なぜ」と「不変条件」に特化する (Document the "Why" and Invariants)**
   ドキュメントにはコード単体では表現しきれない「Elementorとの連携方針」「設計思想」「ビジネス背景」「セキュリティ制約」「不変条件」に特化して記述する。
3. **第 3 条: PR 同梱の同時更新 ＆ 日本語記述 (Definition of Done & Japanese PR)**
   機能追加・修正時には、対応する `docs/specs/`（仕様書）および `docs/adr/`（意思決定）の更新を PR マージの必須条件 (Definition of Done) とし、コードとドキュメントの剥離（ドリフト）を 100% 遮断する。また、**PR（タイトル・概要文・対応内容）は基本的に日本語で作成する**。
4. **第 4 条: アーキテクチャ変更の ADR 記録義務 (Mandatory ADR Trail)**
   テーマ構成の大幅変更、カスタムフックやビルドツールの追加、Elementor連携方針の変更などの重要な意思決定は、必ず `docs/adr/NNNN-<title>.md` として標準フォーマットで記録を残す。

## 🛡️ 2. AIDD セーフティ & ガードレール原則

AIエージェントおよび開発者は、以下の安全規約を厳格に遵守します：

1. **AIと人間の境界（Human in the loop）**:
   - **上流（意図定義）**: 人間が仕様・要件（`docs/specs/`）および受入条件（AC）を定義する。
   - **中流（実装・検証）**: AIエージェントが計画（Plan）→タスク分解（Tasks）→TDD/実装（Implement）→構文検証・マルチデバイス検証（Verify）を実行する。
   - **下流（品質判定・承認）**: 人間が最終差分・受入条件充足を確認し、Git commit / push / デプロイを承認する。
2. **無断 commit / push の絶対禁止**:
   - `git commit` および `git push` は、ユーザーからの明示的な指示または事前許可がある場合のみ実行する。
3. **差分の最小化と不要リファクタの禁止**:
   - 既存コードへの無目的な整形、スタイルの全面書き換え、要求外のリファクタリングを禁止し、PR差分を最小限に保つ。
4. **推測の排除**:
   - 不明点や意思決定が必要な事項は推測で進めず、必ず作業前にユーザーに確認する。
5. **機密情報の完全隔離**:
   - 本番サーバー認証情報、DBパスワード（`.env`, `.env.deploy` 等）をプロンプト外部へ漏洩させず、コミット対象外（`.gitignore`）を維持する。

## 📱 3. マルチデバイス（PC・SP）表示検証義務 (Mandatory Multi-Device Visual QA)

Webページおよびテーマテンプレートの新規作成・修正・デプロイを行う際は、必ず **PC（1280px以上）** および **SP（375px〜414px）** の両方において以下を検証する：

1. **横スクロール・はみ出し（Horizontal Overflow）**: 画面幅を超えてコンテンツやテキストがはみ出していないか。
2. **ヘッダー・ナビゲーション**: スマホ画面でのロゴ、ボタン、メニューリンクの折り返し・文字重なり・はみ出しがないか。
3. **見出し・フォントサイズ**: スマホ画面でフォントサイズが大きすぎて不自然な改行や見切れを起こしていないか。
4. **ボタン・CTA**: タッチ可能な適切な余白（タップ領域）が確保されているか。

## 🔄 4. Spec-Driven Development 開発サイクル

機能追加・修正時は、いきなりコードを書かず以下のステップを踏みます：

```
[要望/起票] ──▶ [Spec定義 (docs/specs/)] ──▶ [Plan (設計/ADR)] ──▶ [Tasks (タスク分解)]
                                                                        │
[Deploy (deploy.ps1)] ◀── [Review/承認] ◀── [Verify (検証/QA)] ◀── [Implement (実装)]
```
